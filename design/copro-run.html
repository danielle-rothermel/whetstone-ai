Algorithm boundary

COPRO owns

Prompt candidate construction, required placeholders, ordered proposal rounds, score feedback, candidate deduplication, and terminal selection.

Shared services own

Provider request execution, physical-attempt identity, retries, evaluation intent, task-matrix execution, evidence persistence, and viewer publication.

One proposal round

  1. COPRO persists the semantic request for the round and each batch slot.
  2. The shared proposal-effect executor derives a stable physical-attempt identity.
  3. Provider evidence is accepted only for the exact request and policy.
  4. COPRO parses and validates each proposal, including required template placeholders.
  5. Each accepted candidate is evaluated through the canonical evaluation service.
  6. The next round consumes resolved Evaluation Evidence, never an unbound score scalar.

Durability claim

Replay is exact only when the provider supports a verified idempotency contract for the stable physical key. Otherwise evidence names at-least-once execution and its duplicate-effect risk. COPRO does not create an algorithm-local effect ledger.

Output

The terminal COPRO result binds its starting candidate, proposal transcript, evaluation evidence references, and selected candidate. Viewer curves are projections over canonical evidence and do not assign authority.
